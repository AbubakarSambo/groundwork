## What live can do that ours cannot, with no decision of Hafsah's

**None on the server.** Every route, sign-in method, setting, scheduled job, email, WhatsApp message, table and column live has is still on `wip/release`. Every difference found is either a privacy or security narrowing (next section, or "Not a loss"), a message that never actually went out on live, or a change to wording. So nothing was restored on the server.

**Three on the screens, with no decision** (S1 to S3 in "For the screens workspace"): the lead's "Begin the last check-in" before the last session or on an open-ended check-in, the Today link to your own leave and spending requests when one suite is off, and the request forms after a passing server fault. They are in `client/`, which the screens workspace owns, so they are handed to it in `docs/answers-from-engine.md` rather than changed here.

## What could not be checked

- **The hosted settings.** Whether the hosted API has the sealing key (`a-secret-kept-sealed.ts`), the Google client id and secret, and the WhatsApp app secret. Without the sealing key an admin cannot save their own WhatsApp number's keys (live let them, unsealed); the back office already needs the same key on live. Without the Google pair there is no Google button, on live and on ours alike.
- **Live data.** Nobody looked at live data, so whether any existing person has no name and a first.last address (H1, H2), or any department lead reads somebody's evaluation check-in today (H3), is not known.
- **Behaviour inside 634 commits beyond what is listed.** Every deleted line in the API outside tests was read; a change that only adds a condition inside a query (for example who a job picks up) was checked for jobs, emails and reads, but not for every one of the 7,000-odd added lines.
